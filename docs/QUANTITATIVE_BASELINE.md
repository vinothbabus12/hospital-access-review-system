# Quantitative Baseline Experiment

## 1. Objective

Measure the impact of the **evidence‑based access review system** compared to a **traditional spreadsheet‑style baseline** on the same synthetic dataset. The primary metrics focus on overall approval rates rather than blanket‑approval counts, which are included for context.

## 2. Dataset

The experiment re‑uses the synthetic data generated by `src/data_generator.py`. This dataset includes:
- **Users** (`users.csv`)
- **Entitlements** (`entitlements.csv`)
- **Usage events** (`usage_events.csv`)
- **Review decisions** (`review_decisions.csv`)

All files are generated deterministically with a fixed random seed (default `42`), guaranteeing reproducibility.

## 3. Baseline Methodology (Spreadsheet‑style)

The baseline simulates how a reviewer would work in a typical spreadsheet:
1. **No usage logs, no peer‑usage baseline, no risk score** are considered.
2. **Active** staff accounts are approved by default (≈90‑95 % of cases).
3. **Inactive** accounts (HR flag) are revoked.
4. No additional logic for high‑risk or low‑usage cases – they are treated the same as any other active account.

This produces a **blanket approval rate** equal to the proportion of active users.

## 4. Evidence‑Based Methodology (Prototype)

The prototype uses the existing evidence engine and risk engine:
1. For each entitlement, `evaluate_all_entitlements` enriches the row with:
   - Usage count, peer‑average/median, risk score, risk level, and a **system recommendation** (`APPROVE`, `REVIEW`, `REVOKE`).
2. The reviewer follows the system recommendation:
   - `APPROVE` → approve.
   - `REVOKE` → revoke.
   - Any other recommendation → **modify** (e.g., request more information).
3. **Blanket approvals** are counted only when the system recommends `APPROVE` **and** the risk score is **≥ 30** (i.e., a potentially risky approval without additional verification).

## 5. Metrics Calculated

| Metric | Description |
|--------|-------------|
| `total_cases` | Number of entitlement review cases processed. |
| `total_users` | Distinct users in the dataset. |
| `total_entitlements` | Total entitlements generated. |
| `total_usage_events` | Number of raw usage events. |
| `baseline_blanket_approvals` | Approvals granted by the baseline (active users). |
| `baseline_blanket_approval_rate` | Percentage of blanket approvals in baseline. |
| `prototype_blanket_approvals` | Approvals granted by the prototype that meet the blanket‑approval definition. |
| `prototype_blanket_approval_rate` | Percentage of blanket approvals in prototype. |
| `reduction_percentage_points` | Absolute reduction in blanket‑approval rate (pp). |
| `relative_reduction` | Reduction expressed as a percentage of the baseline rate. |
| Additional counts (high‑risk, unused, etc.) are derived from the enriched DataFrame and can be inspected in `case_details.csv`. |

## 7. Before‑vs‑After Table

The experiment also creates a CSV (`baseline_results.csv`) containing a human‑readable table with the most important metrics for quick comparison.

## 8. Percentage Improvement Calculations

- **Absolute reduction**: `baseline_blanket_approval_rate - prototype_blanket_approval_rate` (pp).
- **Relative reduction**: `(absolute_reduction / baseline_blanket_approval_rate) * 100`.

Both are shown in the summary and stored in the JSON output.

## 9. Interpretation

A **large relative reduction** indicates that the evidence‑based system effectively curtails unnecessary blanket approvals, focusing reviewer effort on high‑risk or ambiguous cases. This aligns with the project goal of improving security posture while reducing manual workload.

## 10. Limitations

- The baseline is a simplified simulation; real‑world spreadsheet processes may include additional manual checks.
- The prototype follows the system recommendation strictly; in practice reviewers may override decisions.
- Metrics depend on the synthetic data generation parameters (e.g., proportion of inactive users, risk score distribution).

## 11. Reproducibility Instructions

1. Ensure you are in the project root (`hospital-access-review`).
2. Run the experiment:
   ```bash
   python experiments/baseline_experiment.py
   ```
3. The results are written to `experiments/results/` as:
   - `baseline_results.json` – full metric dictionary (excluding the large DataFrames).
   - `baseline_results.csv` – summary table.
   - `case_details.csv` – per‑case decisions for deeper analysis.
4. All randomisation is seeded (`seed=42`), guaranteeing identical results across runs.
